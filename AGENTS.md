# `craft`
The craft plugin ships engineering skills, review agents, and a review workflow engine to other repositories.

## Project
- **Nature**: production; one relaxation — the gate always runs whole, no affected-only mode (realm `@nick/craft`, #118; agreed: owner).
- **Cost of breakage**: external and silent — craft runs in repositories it never sees, and none of its failures fail loudly: a degraded check reads as a clean one (agreed: owner).
- **Consumers**: anyone who installs craft — the Claude Code marketplace (`.claude-plugin/marketplace.json`), the OpenCode delivery, the Codex plugin, the pi package; they learn of breakage only by its effects — a skill that never triggers, a review that silently drops a check, an agent advising on code it never read (agreed: owner).
- **Stack**: Node.js 22 (CI pin), ESM JavaScript with JSDoc types, no runtime dependencies; the OpenCode plugin in TypeScript; the `craft` CLI in Rust (toolchain pinned in `cli/rust-toolchain.toml`); skills and agents are Markdown with YAML frontmatter.
- **Gate**: `npm run gate` (the Rust CLI — CI's `rust` job, "Commands").
- **Layout**: code map — "Project structure" below and `MAP.md`; gotchas — realm rule nodes on the steps they constrain.
- **Feedback reflection**: yes — template default.
- **Workflow-suite interop**: none — no coercive suite installed.

## Persistence rules
State lives in the **repo** or in the **realm** — nowhere else. The harness's built-in memory (memory directory, conversation summaries, `/tmp`, machine-local files) is **forbidden entirely, not by category**; the temporary directory is only the session's scratch, and the session cleans it up.
- **Repo**: code, configs, rituals (how to act here), branch state.
- **Realm**: decisions, substantive questions (vimarshas), plans (the transformation map), lessons; gotchas — per the "Layout" slot. Do not restate the realm in the repo — link it.
- **Case** (a conversation on a realm node): a one-off brief, question, agreement, acceptance; the progress and outcome of work — as lines of its summary ("Work runs in the realm" below); the state of what the work changes — in the realm.
- **Retrieve state, do not recall it.** No source for "we decided…" — read the realm or the repo before acting.
- **A node is not recorded until the thing pulling it is named** — which kriya breaks if it disappears? Hiding places and the form of a write — the `writing` skill.
- **Whose fact is this?** — ask always, over the harness's memory instruction; before finishing, place every durable fact of the conversation: a code property, ritual, command or procedure of this repo → this file; a gotcha → its home by "Layout"; the meaning of code (decisions, grounds, links) and knowledge that outlives a refactor → the `@nick/craft` realm, a decision as a node at once; a substantive question or obligation → a vimarsha; a one-off → a word in a case; work progress → node modes; about another project → that project's realm. A rule or method of this project itself — here, by authority. The user's own is not written here: where it lives — the `iskron` door.
- **Project instructions are held by committed working-tree files (AGENTS.md, the hooks file) and the project realm** — never a global instructions file, harness memory, or user hooks; personal preferences are not copied into the project; installing a delivery (bridge, plugin) is delivery, not configuration.
- The memory directory is **evacuated and frozen**: the `PreToolUse` memory guard in `.claude/settings.json` blocks writes into `~/.claude/projects/*/memory/` (exit 2); no stub is created (an existing one stays as it is); it does not read the `rituals:` field — switching `guard` off means removing it. Evacuate before freezing; delete nothing unread. Two arms: `Write|Edit|MultiEdit|NotebookEdit` tests `file_path` (or `notebook_path`) as a resolved path — Windows separators normalised, symlinks followed, `..` applied, case-insensitive; `Bash` tests the command for a write shape aimed at that path (`>`/`>>`, heredoc, `tee`/`cp`/`mv`/`rm`/`touch`/`install`/`mkdir`). Reads are not blocked, nor is a write the regex cannot see (an editor, a path built at runtime) — the guard catches the reflex; it is not a sandbox.

## Session lifecycle
One line per rule; the full norm is the cross-cutting norms of the `iskron` skill.
- **The realm is the work, git is how we got here.** SHAs, branches, PR numbers, "merged" never enter the realm (bodies, names, attributes); provenance goes in a write's `reasoning`. In a case they are written freely.
- **Session start** — the "Start" section of the `iskron` door before acting and until readiness, not only before reading. Addresses — from the cover; entry by a `start` line, the receipt and a subagent's own bridge — by the door's `start.md` reference.
- **Cleanup — with each finished piece** ("Cleanup" in the cross-cutting norms of the `iskron` skill): scratch and your own development caches — in the same move, the tree and the branch — "Branch discipline"; leave cases where your move is no longer awaited, closing your lines with their outcome, then `leave` (the lead — `propose_close` or a handover of the lead). Sit only where you await an answer or lead something unclosed.
- **Realm craft — with whoever decides**: reading for a decision, the decision, weaving, integration and acceptance ("Realm craft" in the cross-cutting norms of the `iskron` skill). To subagents on their own satellite bridge — the bulky work on a decision already made: code, gate, review, verification, editing the many nodes it touches with references to the decision and the neighbourhood; a search along the `recall` ladder — `recaller` (the decider opens the find), the intake of a complex story — `ingester`; the launcher checks the result.
- **Starting work: realm, then project, then code.** (1) realm reconnaissance (`entry`): what is recorded about the site of the change, open vimarshas, what was decided and rejected; (2) the integration field (`integrity`, section below); (3) design (`design`), then code. Skip only on an explicit "just work" or another named protocol — the reconnaissance debt goes to reconcile; human silence is not permission.
- **A decision goes into the realm the moment it is made**, wherever it came from (chat, socket, agents agreeing) — into the repo's holon as an edit of what it touches and its links, the thesis as a node of its own, modes by `writing`; what counts as execution — in the node; who decided — in `reasoning` and the case, not in the node. A changed situation — the same, at once.
- **Describe work before it begins — as what it is.** One-off work — in one case: the brief and agreement as words, progress and outcome as lines by the door's `cases.md`; arrived without a case — open one (`open_room` on the subject's node or `iskron_case(action="talk", about=<subject>)`) before the first external change. Into the realm — the transitions it changes, and decisions. A vimarsha is only a substantive question or obligation; a kriya is a repeatable transition. Telling a task from a legitimate one-sided edge kriya — `reconcile`, pass 2.
- **Work runs in the realm** — the cross-cutting norms of the `iskron` door; before a move in a case read its `cases.md` reference, leading a case — `leading.md` too. The realm/case distinction, addressing, the form of progress and outcome and the handover of the lead live there; the method is not copied here.
- **Merge → realm.** A push that opened or updated a PR shipped nothing; the sequence hangs on the merge event, not on a lull. Every act is mandatory — except for work by reference from an agent (a brief by references, a report in a case): there weaving, closing along the axis and reconciling are the setter's, and the doer's are the transformation seed and the delivery modes (`vahta` skill):
  - **Weave** (`weaving`): what shipped — into the target system as nodes and edges, not a paragraph; repo mechanics stay in git. Zero nodes and arrows after a substantive wave — say plainly why.
  - **Advance the map**: open work — `anga` to the transformation; one `genre=hint` seed per transformation — only what cannot be recovered by reading the realm and the cases; live cases — a pointer to reading them (`iskron_case(action="at")`, `read`), a number only where an essential choice cannot be recovered otherwise.
  - **Switch modes** by evidence on the carrier (`REALITY.md`, **reality-audit**), not by the merge: the merge moves the nodes of what the code carries; a practice (`anagata→vartamana`) — a rollout or run seen on the carrier (`anumita`), observed — `pratyakshita`.
  - **Close along the axis** (`inquiry`): `addressed_by` to the carrying node; `visarjana` when the answer stands as a node, the repo shows it and reality shows it as far as reachable (where not — the user's word); otherwise put it to the owner. In the same move — the `posed_to` inbox (a change at the anchor wakes them, not age), `propose_close` with evidence.
  - **Reconcile** (`reconcile`): nodes against code, code against the realm, discarded options recorded and referenceable; the remainder as vimarshas.
  - **Feedback reflection** — at the merge and at a session close without one: experience *about the method* (a skill, rule or surface failed or surprised) — as a case, not an opinion, after checking it was not said already, into the work realm anchored on the tool's node and addressed to its steward; about the method in general — by the `feedback` skill's route. Zero records is a valid outcome.
  - **Vocabulary pass**: borrowed words (the list — principle 8) in the text and nodes you land — name each to the human and ask what it is called in this project; never substitute on your own.
- **A design is not ready until its decisions, risks and lifecycle are in the realm**, whatever skill elicited it; an external design/spec file is a draft for intake in the same session — the realm holds the decisions. Without the owner: decisions and risks — now, the transformation — with its telos awaiting confirmation.
- **Execution suites lead execution** (planning, TDD, debugging, review); the realm carries memory and design: decisions and risks born in execution go into the realm before the session ends.
- **A claim you made is not a claim you accept.** A behavioural claim is closed by a cold `verifier`: the brief is the claim, the carrier and the falsifier from `REALITY.md`; wait for the verdict. No role available — observe the carrier yourself, never the source.
- **Hook merge**: entries from different suites coexist in the hooks file — add alongside, never overwrite someone else's.
- The start, push and merge rituals are carried by the delivery by the cover; the memory guard — Claude Code: in the repo (`.claude/settings.json`), OpenCode: carried by the delivery. This repo still holds its own start, push and merge hooks in `.claude/settings.json` until a service session observes the delivery's replacement (alignment case №77); they stay until then. Craft's own entries beside them stay regardless: the pre-push branch-freshness probe (`PreToolUse` `Bash`) and the local pull arm of the merge hook — it wakes on a pull whose target copy is on `main`/`master` (`git pull`, `git -C <dir> pull`, `cd <dir> && git pull` and chains of such `cd`s, `git -c <k=v> pull`, with or without `rtk`) unless the pull reports "Already up to date" (realm `@nick/craft`, node #235); an `iskronify` re-projection of the hooks must carry both over. A visible refusal (git's `fatal:`/`error:`/`! [rejected]`; the forge's `error:`, `GraphQL:`, `X `, "not mergeable") wakes neither the push nor the merge hook, nor does a tags-only push.
- **Keep this file honest.** The contract is the number after `КОНТРАКТ AGENTS.md:` at the start of the `iskronify` skill description: compare it with the cover's `contract` without loading anything. Higher than `contract`, or the sources moved after `stamp` (`git log -1 --format=%cd -- .github/workflows/ci.yml .claude-plugin/marketplace.json integrations/claude-code/.claude-plugin/ lib/ package.json cli/Cargo.toml`) — run `iskronify` as the first move, in a clean tree and a work branch, by its "Who executes the run" rule; the run does not wait for the human, the order of slots — Step 1 of `iskronify`. **Lower than `contract`** — the file is ahead of the delivery: do not lower it and do not call the run; update the shadowing copy of `iskronify` and re-read the description. A line of this file diverges from the skill — say so aloud (in a case to the setter, otherwise to the human): `contract` lower — the skill is right; higher — the file is right; equal — a template defect, feedback to the skill delivery's steward (`feedback` skill).
- **Keep the toolchain fresh**: updates are on by default — take them as the channel delivers them. A channel without auto-update (an unpacked copy) — check the version before the session, or move.

### Stage self-check
Gate green and a coherent stage finished (a branch about to go to the cold review and the push, or you are about to touch nodes beyond the initial ones) — re-read the branch diff against trunk: bugs, fragile spots, weak error handling, DRY/SOLID violations, missing or useless tests, files over 150 lines, god-units. Fix in the same branch, or say plainly that nothing surfaced; do not invent findings. Per stage, not only at the end.

### Cold review of the batch
- **Self-check always, the cold review after it — where due below**: you see your own work as you intended it.
- **Two stages, not a round on every PR** (realm `@nick/craft`, #254). A finished batch's branch — one light independent review of its diff by the `reviewer` role; an unfinished feature or an intermediate PR is not put through a full review. The full review — once, on release-please's release PR before it merges: the `reviewer` role over the whole diff since the previous tag, with its integration report; Medium and above are fixed in their own branch before the release merges, Low — a line in the release PR body. After a fix — a check of the changed delta and the findings it touched; a pull of `main`, a rebase or a new SHA with no change of content is not a new round. A second model family — only on the human's word, with names. CI, tests and a targeted check of a security or data-loss threat stay on every batch.
- **The cold review comes before the push and before the PR, not after** (realm `@nick/craft`, #127): after the self-check, the `reviewer` reads the local branch at its commit, not `origin/<branch>`; blocking findings are closed before the push; `git push` and `gh pr create` follow the verdict. An open PR is an invitation to merge, and a review that lands after the merge has lost. A deliberate divergence from the iskronify template, which opens the PR in the same move as the push: an `iskronify` re-projection must carry this order over.
- No hook guards this order — a hook's context reaches the model only after the command has run (realm `@nick/craft`, #289), so the post-push line can only catch a push that came first; the order is yours to hold.
- The review — by the `reviewer` role, **in a separate worktree**: where the spawning tool gives isolation (Claude Code — `isolation`) — through it; where it does not (OpenCode) — the lead lays a detached tree (`git worktree add --detach .worktrees/<name> <head>`), the path goes into the brief as "work only there", the no-edit rule as the second line; the report says "manual isolation". Neither — say that there was no cold review.
- The reviewer's brief: the launch line `start <realm> <role> <case №N>` of its child case, the whole diff of the local branch against trunk (`origin/main...<branch>`, at the commit the brief names), the focus holon with its steward role and references to the realm nodes the diff touches, not a retelling; the integration field and report — by the `reviewer` role. `NEEDS_CONTEXT` is a realm defect: design further, weave, pose vimarshas, review again. A finding you disagree with is rejected with a recorded "why" (in the PR or on the node).
- **Only Low findings left — no further round**: the PR is opened and merged as it stands; the Low findings are dropped, one line each in the PR body. A follow-up branch only for a Low that visibly hurts the plugin's consumer, named in the PR body with that reason (realm `@nick/craft`, #220).

### Role file tails
#### reviewer
- Read the diff and files by the local branch the brief names — the review comes before the push, so `origin/<branch>` may be missing or stale (realm `@nick/craft`, #127): `git fetch origin`, then `git diff origin/main...<branch>` and `git show <branch>:<path>`, and check that `git rev-parse <branch>` is the commit the brief names. A branch with no local ref (release-please's release PR) — read `origin/<branch>`.

### Branch discipline
One branch and one PR per batch, until it merges: its items, follow-ups and subagents' work go into it locally. **A branch lives in its own worktree inside the repo** (`git worktree add .worktrees/<branch> -b <branch> origin/main`; `.worktrees/` is in `.gitignore`), not in the main copy and not beside the repo: sessions share the main copy, and a `checkout` there wipes someone else's work. After a merge: `git worktree remove` your tree, `git branch -d` the merged branch and others already in `main`, your development caches; `git pull` in the main copy (it stays on `main`); weave what shipped into the realm; the next branch from a fresh `origin/main`; confirm the cleanup before the next task. **An abandoned tree** (its branch in `main` or deleted on the forge, the copy clean) may be removed by any agent of the repo (`git worktree remove`, `prune`, `git branch -d`); uncommitted or unmerged work is not touched — name it to its holder or the human.

## Working principles
1. **Think before code.** Name your assumptions; when unsure, ask *what exactly* is unclear. **A question to a human is asked in words, not with a picker tool**: in text — only to whoever is answering now; one that outlives the turn — an `ask` card in the case ("A question to the human" in the `iskron` door; no case — take one; no seat — their standing bridge); the harness's option-picker tool — never. Object when you see a simpler move or a false premise. Touch the live system before trusting a type, a name, a doc.
2. **Simplicity first.** The minimum for the task; no speculative features, abstractions for one-offs, handling of the impossible. Validate at boundaries.
3. **Stay inside the repo boundary.** Edits only in the working directory; outside it — reading carriers, the session's scratch and the delivery's home. Another holon — a vimarsha on its node (`anga` to the transformation) and a word to its steward in a case (`iskron_case(action="talk", about=<subject>)`). **Do not take someone else's code into context** — no reading, no clone, no subagent reconnaissance: what is needed comes from the realm (that repo's holon, its phenomena, relays, vimarshas) or a word to its steward; what is in neither — a `posed_to` vimarsha to them.
4. **A second implementation is an event to report.** Derive both places through `integrity`, name them to the human, propose reunification or a named fork; a new consumer gets its edges in the same move.
5. **Surgical changes.** Touch what the task needs; do not reformat or refactor neighbouring code; keep the style; the linter is authoritative; delete only what your change made dead — flag the rest, do not delete it.
6. **Goal-driven execution.** A bug — a failing test before the patch. Multi-step — `step → check` pairs. Runtime — in the real environment. The falsifier before you look; observe the carrier (`REALITY.md`), not the source.
7. **Read before answering an open question** — from what is recorded, not from training data (`recall` skill). A search hit is a lead, not data: structure and links through `iskron_look`, `iskron_orient`; to a subagent — reconnaissance of code and files (`reader`), a realm search (`recaller`); reading the find for a decision is yours.
8. **Think in the realm, speak the project's language.** The realm's vocabulary (kriya, phenomenon, holon, role, vimarsha, modes) is for reasoning; to the human — the project's words (skill, agent, workflow, lens, gate, finding, verdict) until they use it first. Borrowed words about the work — ticket, task, sprint, backlog, epic, story, done, blocker, committed — never substitute on your own: name them and ask what they are called here ("Vocabulary pass"); say: the question, the change, what is open, what this resolves.

## Integration field — from the realm only
- The root of the walk is the focus holon `#1` and the steward role `#3` from the cover. Do not keep a list of shared surfaces or consumers here and do not ask the human for one — someone else's thing the realm does not model belongs under "External surfaces".
- For each change name the nodes whose embodiment is in the diff and run `integrity`: a phenomenon — `iskron_orient(lens="trace")` both ways; a kriya — the `next` thread and the `ahara`/`utpatti`/`upadhi` relays; crossing into another holon — to its steward role.
- A dependency the walk did not find is a model defect: design (`design`), weave (`weaving`), waiting — a `posed_to` vimarsha and a word in the case. A public handle with no trace in the realm is either unneeded or a realm debt. A new consumer is in when the code and the edges appeared in one move.

## External surfaces — what you use and do not own
Someone else's API, SDK, CLI, protocol, schema — here above all the Claude Code harness contracts (skill and agent frontmatter, plugin and marketplace manifest schemas, the Workflow tool API, MCP tool names) and the host CLIs the `craft` binary drives (`claude`, `codex`, `pi`, `opencode`): memory of them is indistinguishable from knowledge, and a wrong name diverges on a live call.
- **Before the work, pin the part of the surface you touch** as a realm node, with the version.
- **Pratyaksha before shabda**: observation by your own hand (a call, `--help`, `claude plugin validate . --strict`, the installed package's types) outranks docs, docs outrank memory, memory is not a source. `pratyakshita` only for what you observed.
- **Thread the link**: the surface node is an `upadhi` (or `ahara`/`utpatti`) on the kriya that acts through it.
- **Keep it in step**: a divergence or a new version — fix the node in the same move; lower the epistemics if you did not observe it.
- Source that works with a surface carries `(realm @nick/craft, node #N)` — and you read that node before the work.

## Project structure
Layers: `src/` engines and `lib/` modules → built into `integrations/claude-code/workflows/`; the `craft` binary (`cli/`) runs the review for every host, reached through `bin/craft`; each `integrations/<host>/` holds one host's delivery or says where it lives. `MAP.md` maps the contents.
- `skills/` — 39 skills, one directory each with a `SKILL.md`.
- `integrations/claude-code/` — the Claude Code plugin: `.claude-plugin/plugin.json`, `agents/`, `hooks/`, `workflows/`, and `skills`, `lib`, `content`, `src` and `README.md` as symlinks to the root ones (a load in place, `--plugin-dir`, follows them into the checkout). The root marketplace's entry installs it from the `claude-code-plugin` branch (`"source": { "source": "url", "url": "https://github.com/gurinderu/craft.git", "ref": "claude-code-plugin" }`, no entry version: the version is the one in its `plugin.json`), whose every commit is one release's delivery with the links dereferenced into real files, written by `.github/workflows/claude-code-plugin.yml` (called by release-please on each release) through `node lib/materialize-claude-code.mjs --branch claude-code-plugin --message <text>` (a clean checkout of the tag; it commits the branch, the job validates the committed tree with `claude plugin validate --strict` and pushes it) — a clone of `integrations/claude-code` with `core.symlinks=false`, the Windows default, would hold one-line text files where the links are, and the harness would cache them as they are; the branch has none: on Linux with `core.symlinks=false` the plugin installs with all its files. Not observed on Windows, where the hooks are POSIX shell commands run by Claude Code's shell. The branch is never edited by hand, and a change to the delivery reaches it only with a release.
- `integrations/claude-code/agents/` — 5 Claude Code review agents (`rust-reviewer`, `nix-reviewer`, `rust-architecture-reviewer`, `rust-security-scanner`, `rust-miri`) and `engine-service`, the review engines' service-step agent.
- `integrations/claude-code/hooks/` — `hooks.json`: the SessionStart hook, run as `lib/session-start-hook.mjs`; the UserPromptSubmit and SubagentStart hooks, run as `lib/work-hook-entry.mjs`; the PreToolUse hook on the Agent tool, run as `lib/reviewer-dispatch-hook-entry.mjs`.
- `src/` — the engines as authored, scripts for the Workflow tool: `review.js` (the review: the driver of the Rust CLI's step protocol, the hottest surface), `rust-audit.js`, `triage-findings.js`.
- `integrations/claude-code/workflows/` — the same engines as shipped (each with its `.js.map`): generated from `src/` by `npm run build:engines` and committed (the harness loads them from here); never edited by hand.
- `content/` — the review's knowledge as data: prompt templates (`prompts/`, `{{name}}` placeholders filled by `lib/content.mjs`'s `render`), agent answer schemas (`schemas/<name>.schema.json`), language profiles (`profiles/`) and the parity files shared with the CLI's tests (`parity/`); the build inlines them into `integrations/claude-code/workflows/`, each content file's base name unique.
- `cli/` — the `craft` Rust CLI, a cargo workspace: `bin/craft` (the command: `init`; `review start | submit | status | gate | comment`, the step protocol the Claude Code engine drives; `review run --backend codex|pi|opencode`, its own driver of the steps; `review probe`), `crates/craft-agent` (agent backends — the `claude`, `codex`, `pi` and `opencode` CLIs; the Anthropic API not implemented — and the concurrency runner), `crates/craft-review` (the review step by step: its work, its state between steps, its report), `crates/craft-tui` (the progress view), `test-support/`; its version is the plugin's (release-please moves `cli/Cargo.toml` and `cli/Cargo.lock`), and each release carries its binaries.
- `bin/craft` — the POSIX wrapper the shell-run hosts (Codex, pi, OpenCode) call: it runs `~/.craft/bin/<version>/craft`, first downloading and checking the release binary of the plugin version (the cache layout is `lib/craft-bin.mjs`'s); `CRAFT_BIN` runs a local build.
- `lib/` — the CI checkers (`check-*.mjs`), the gate (`gate.mjs`), the run-record write path (`run-record.mjs`, `run-logging.mjs`, `craft-log-run.mjs`), the modules the engines import, the engine harness (`engine-harness.mjs`), `craft-bin.mjs` (the binary cache), `craft-review-run.mjs` (one `bin/craft review run --events json` for a host's tool, shared by pi and OpenCode), `pi-extension.mjs` (pi's `craft_review` tool), the hooks' entries, `analyze-runs.mjs`, and their tests.
- `integrations/opencode/` — the parallel OpenCode delivery: `agents/`, `commands/`, `plugin/` (TypeScript; its `review` tool runs `bin/craft review run --backend opencode` through `lib/craft-review-run.mjs`), `scripts/`, `install.sh`.
- `.codex-plugin/` and `.agents/plugins/` — the Codex plugin manifest and marketplace, at the root because Codex leaves symlinks out of the plugin root it copies; the manifest's `hooks` names the Claude Code hooks file; `integrations/codex/README.md` says why.
- `integrations/pi/` — the pi package's `craft-review` skill (`skills/`); the root `package.json`'s `pi` manifest loads it and the extension `lib/pi-extension.mjs`, nothing else.
- `.claude-plugin/` — the marketplace manifest.
- `evals/` — the skill-triggering corpus (`evals.json`) and its README; `docs/` — `LESSONS.md`, `observability.md`.
- `.claude/settings.json` — the repo's hooks (committed); role agents in `.claude/agents/` are machine-local projections, not in git.
- `MAP.md` — a map of the repo's contents; `README.md` — the human-facing entry point.

## Code conventions
- **Meaning lives in the realm, code references it**: a comment carrying rationale, discarded alternatives or the shape of an integration is a node; in code — "(realm `@nick/craft`, node #N)", for the discarded too ("not cached: #N"). Mechanics — in words in place. Having cited a node, check it says that; it diverged — fix the node. This repo is public (MIT, marketplace): references belong in `lib/`, `src/` and `cli/` code, not in `README.md`, `MAP.md` or skill bodies.
- **A skill's or agent's `description` is delivery, not decoration**: a skill loads by its description, so a rule living only in the body never fires. Change a skill's behaviour — re-read its `description` in the same move.
- **No runtime dependencies**: what ships rests on the Node standard library; the root `package.json` is `private` with devDependencies only — the test runner (Vitest, realm `@nick/craft`, #140) included (#124).
- **Typed errors in the Rust CLI**: the library crates in `cli/` return typed `thiserror` errors; `anyhow` only in `bin/craft`, where the error is printed for the user. A reason an agent's answer is retried (`validate::check`, `handoff::read_answer`) is data for the retry prompt, not an error, and stays a `String`.
- `eqeqeq` is `{ null: 'ignore' }` on purpose: `x != null` means "neither null nor undefined"; do not "fix" it to `!==`.
- **Testing discipline**: unit tests cover `lib/**` and `integrations/opencode/plugin/**`, `cargo test` covers `cli/`; workflow scripts are exercised through `lib/engine-harness.mjs`, skill bodies only by static checkers. No coverage threshold. Tests are local to the change: a component has its own module and tests, a test of the layer above checks only the composition. Logic that must be executed and sits in `src/*.js` is extracted into `lib/` and imported back; the build bundles it (realm `@nick/craft`, #210).
- **Gotchas do not live here**: they are rule nodes on the realm steps they constrain — #119–#126 for the gate, the two deliveries and run records; reference them here and in code.

## Running a review
- **A review request goes to the background**: dispatch the `reviewer` agent with `run_in_background: true` and keep working; report the verdict when it completes. A synchronous review only on explicit request.
- **Always a fresh agent**: every review, a delta check after a fix included, is a new agent with a clean context — never `SendMessage` to a prior one; restate the diff range and intent each time.

## What to update when
- `AGENTS.md` — **what can be learned from a realm node is not written here**; it holds what is needed before an agent reaches the realm (commands, the entry into orientation, invariants a linter cannot express, forks that must stop you) and changes when those change. Cleaning out prose means moving it into the carrying nodes, not deleting it.
- `REALITY.md` — when a claim class's carrier appears, changes or turns out unreachable; dated measurements go to the realm.
- `MAP.md` and "Project structure" — in the same commit that moves, renames or adds a component's files.
- The `@nick/craft` realm — every merge ("Session lifecycle").

## Git workflow
- **Forge**: GitHub (`https://github.com/gurinderu/craft`); CLI `gh`. Observe with `gh pr checks <n> --watch`, `gh pr view <n>`; trunk as the forge sees it — `gh api repos/gurinderu/craft/commits/main --jq .sha`. Never treat a local ref as current — `git fetch origin main` first.
- **Conventional commits** (`feat:`/`fix:`/`chore:`/`refactor:`/`docs:`/`test:`) — release-please parses them, so the prefix carries the version; branches `feat/…`, `fix/…`, `chore/…`; PR titles in the same format.
- **PR body — short**: what changed and the case number, plus the lines the review rules above put there (dropped Low findings); work progress and case lines are not copied into the PR.
- **No co-author trailer and no "Generated with Claude Code"** — neither on commits nor in PR bodies.
- **The gate is one call**: `npm run gate`, always whole (the owner's accepted relaxation — no affected-only mode; realm `@nick/craft`, #118), on the batch's head before the push; do not assemble its steps by hand; read its raw exit code (the audit and semgrep rows need the network — offline they are CI's); there is no pre-commit hook. CI calls the same gate on the batch's PR and on `main`.
- **Review, push, then PR** (realm `@nick/craft`, #127): the cold reviewer reads the local branch in its own worktree; push once its verdict is in and its blocking findings are closed, then open the PR. A batch's branch whose review is done does not live without a PR.
- **Definition of done**: a PR into `main`, `gh pr checks <n> --watch` green (four jobs: `test` — `npm run gate` plus the shipped-dependency audit —, `semgrep` and `rust` gate; `quality-delta` always ends green and is read, not waited on; a red one means reading the log for the failed step), merged without conflicts. release-please cuts releases in a separate PR — merging a feature is not a release; `CRAFT_VERSION` in `review.js` moves with the manifest.
- **The `claude-code-plugin` branch is moved by the release job** (`claude-code-plugin.yml`, called with each release's tag; the 0.42.0 release created it). A dispatch (`gh workflow run claude-code-plugin.yml -f ref=vX.Y.Z`, the input required, no default) runs only from `main` (GitHub dispatches only a default-branch workflow) and only re-publishes the branch from a release tag: the job refuses any ref that is not `vX.Y.Z`, not a tag on origin at the checked-out commit, or whose `plugin.json` version is not that tag's, so it never ships unreleased content under the last release's version.
- **Never** `--no-verify`, `--force`, `--no-gpg-sign`, `git reset --hard` without an explicit instruction.
