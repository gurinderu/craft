Walk the changed steps IN ORDER, as the operator will, and for each command say to yourself what it does in the system it talks to (kubectl, gh, helm, terraform, curl, psql, aws, nix …), then look for: (a) STATE IT ASSUMES AND DOES NOT CHECK — a resource, label, annotation, field or reference the step relies on that the command it reads from does not actually show (a reference pod annotations do not carry, an object name only a template binding resolves, an id copied from an earlier step's output that the procedure never prints), a precondition no earlier step establishes or verifies; (b) RACES BETWEEN STEPS — a controller, operator, autoscaler, cron or another operator acting between two steps, so that what step N read is stale at step N+1 (a pod recreated, a lease re-acquired, a resource re-reconciled back); (c) IRREVERSIBLE STEPS — deletes, overwrites, force flags, schema or data changes, merges and releases: what stops a wrong one (a dry run, a check, a backup step before it), and what happens on a retry after a step half-succeeded; (d) DRIFT FROM THE CODE — a step whose command, flag, name, path, port, label or order no longer matches what the code, manifests or charts beside it in this repository do (open them); (e) a step that cannot run as written (a missing namespace or context flag, a shell construct that breaks when pasted, a placeholder never named). Judge each step against the external systems' behaviour from their source at the deployed version when the EXTERNAL SOURCES block below lists it — cite `<dir>/<path>:<line>` in `whereChecked`; a claim about a system not listed is an open question unless you open its source yourself. Prose, wording, formatting and style are not findings. Rate by the harm the procedure would cause when an operator follows it (review-rules severity.md): a step that deletes or corrupts what cannot be restored is data-loss or irreversible; one that wedges a system an operator must recover by hand is operator-recovery; a wrong command that fails loudly and harmlessly is Low.
