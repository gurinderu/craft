tests as a COVERAGE ADVERSARY (not a presence check): enumerate what a regression could SILENTLY break, then check each has a test that would FAIL on that regression. The litmus test: if you deleted the production line/branch that carries a contract, would the suite still pass green? If yes, that contract is UNTESTED → finding (cite the missing test). Cover, at minimum: (a) every NEW branch and every distinct ERROR CONTRACT the code / handler / OpenAPI (or other documented interface) promises — not-found→404, forbidden / wrong-owner, bad-request→400, conflict→409, a typed 4xx that must not collapse into a 500 — each needs a test asserting THAT status/error, not just the happy path; (b) every SECURITY / AUTHORIZATION boundary — tenant or owner isolation: is there a test exercising a DIFFERENT user/tenant/scope and ASSERTING denial? A single-user happy path does NOT prove isolation; on a NEW authz-guarded endpoint a missing cross-tenant/cross-owner denial test is a HIGH-severity gap; (c) every behavioral CLAIM in the stated spec — identity preserved / "in place", a state that must stay put or transition exactly once, a field that must be scrubbed, an idempotent no-op — each needs a test that pins it and would fail if the claim were violated; (d) self-exclusion / dedup / unlink / bookkeeping guards — a uniqueness check that must exclude the row itself, a back-reference that must be cleared. TWO DIFFERENT FINDINGS — never merge them into "no test"; set `testGap` on each: `missing` — no test pins the behaviour (vacuous tests such as assert!(true) or no assertions count as missing); `weak-assertion` — a test EXISTS and still passes green under a named regression of the changed behaviour: it asserts only the status or an annotation, a mock ignores the request body or fabricates the response, or only one of two sides (ingress/egress, read/write, create/update) is covered. Put the regression in `regression`: what the running system would then do that the suite lets through ("the handler stops applying the field and still answers 200"); and in `regressionAt` the file:line of the PRODUCTION code that regression breaks (the line a verifier checks reaches production; the finding itself cites the test); a weak assertion that cannot name a regression is not a weak assertion. SEVERITY: a missing test with no named regression is Low (optional), `regression` empty. A missing test takes the severity of the defect it would catch once you name that defect in `regression` and its harm (review-rules severity.md) — the cross-tenant gap in (b) names a security harm, hence HIGH. A weak assertion is NOT Low by default: its `harmLevel` is the production harm of the regression it lets through (behaviour, data, access — not `text` unless the regression only changes text or style) and its severity that level's, capped at Medium (should-fix): the test is the missing guard, not the defect. A weak assertion whose regression changes only text or style stays Low.
