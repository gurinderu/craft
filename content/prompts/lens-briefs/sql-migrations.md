schema migrations against a live PostgreSQL database (PostgreSQL semantics; another engine only where the repository says so) — what the migration does to production while it runs, and to the code deployed beside it. Load the sql-review skill and work its migrations checklist; its lock table and rewrite table are the facts, not memory. For EACH changed migration statement, in order: (1) LOCK: name the lock it takes (most ALTER TABLE forms take ACCESS EXCLUSIVE; CREATE INDEX takes SHARE, blocking writes for the whole build; ADD FOREIGN KEY takes SHARE ROW EXCLUSIVE on both tables) and what runs while it is held — an instant catalog change, a full scan, or a rewrite. A table lock is held until the END OF THE TRANSACTION that took it, not the statement: every later statement of the same transaction runs under it, and migration tools (sqlx, diesel) run each file as one transaction by default. A lock queued behind a long transaction blocks every later query on the table, so a brief ACCESS EXCLUSIVE without a `lock_timeout` is still an outage risk on a hot table. (2) REWRITE: does it rewrite the table and its indexes — ALTER COLUMN TYPE unless binary-coercible (int→bigint rewrites; varchar(n)→varchar(m>n) or →text does not), ADD COLUMN with a VOLATILE default (gen_random_uuid(), clock_timestamp(), a serial/identity) or a STORED generated column; ADD COLUMN with no default or a non-volatile one (a constant, now()) does NOT rewrite since PG 11. (3) NOT NULL: ADD COLUMN … NOT NULL without a DEFAULT fails on a table that has rows; SET NOT NULL scans the table under ACCESS EXCLUSIVE unless a validated CHECK (col IS NOT NULL) exists (PG 12+) — on PG 18+ a NOT NULL constraint can also be added NOT VALID (`ADD CONSTRAINT … NOT NULL col NOT VALID`) and then validated; a new CHECK or FOREIGN KEY without NOT VALID + a later VALIDATE CONSTRAINT scans under its lock — and the two-step forms (NOT VALID then VALIDATE; CHECK NOT VALID, VALIDATE, SET NOT NULL; PG 18+ NOT NULL NOT VALID then VALIDATE) are safe only when the NOT VALID step commits before VALIDATE runs: the two in one transactional migration file keep the NOT VALID step's ACCESS EXCLUSIVE (SHARE ROW EXCLUSIVE on both tables for a foreign key) through the whole scan, a must-fix on a large table (MIG-009). VALIDATE and the SET NOT NULL after it may share a transaction (the scan runs under SHARE UPDATE EXCLUSIVE, and SET NOT NULL's ACCESS EXCLUSIVE is then brief) — no finding there. (4) INDEX: CREATE [UNIQUE] INDEX on an existing table without CONCURRENTLY; CONCURRENTLY inside a transaction block fails, so check how the migration tool wraps the file (sqlx: a `-- no-transaction` first line; diesel: `run_in_transaction = false` in the migration's metadata.toml) that the concurrent build is the file's ONLY statement (several statements sent as one query string run as an implicit transaction block and fail the same way), that the table is not a partitioned parent (CONCURRENTLY is refused there: build it on each partition, then CREATE INDEX ON ONLY the parent and ATTACH each), and that a failed concurrent build's INVALID index is handled. (5) BACKFILL: an UPDATE/INSERT … SELECT over a large table in one statement or in the same transaction as DDL — one long transaction holding row locks (and any DDL lock taken before it), WAL and replication lag; it belongs in batches, outside the schema migration. (6) ROLLOUT ORDER: during a deploy the OLD code runs against the NEW schema (and, if migrations run after the rollout, the new code against the old): a dropped or renamed column or table still read or written by code on the base, a new NOT NULL column old INSERTs omit, a changed type old code decodes, an enum value old code cannot parse — find the code that touches the object (Grep the repository, Rust and every other language) and name which side breaks. (7) REVERSIBILITY: a down migration that is missing where the repository keeps them, or that cannot restore what the up removed (DROP COLUMN/TABLE, a narrowing type change, a lossy UPDATE). (8) MIGRATION NUMBERS: list the migrations already on the base and on the trunk — `git ls-tree --name-only <diff base> -- <migrations dir>/` (the diff base named below) and the same at the remote default branch (`origin/HEAD`, else `origin/main`) — and compare with the ones this diff adds: a reused version number or timestamp, a new version that sorts BEFORE the latest one already on the trunk (refused by tools that forbid out-of-order, silently never applied by tools that record only the current version), or an EDIT to a migration the base already holds (a checksum mismatch, or a change that never reaches a database that applied the old text). HARM: a table locked or rewritten under traffic, or a deploy whose migration fails, is `outage`; data dropped or truncated that no durable source restores is `data-loss`; both are must-fix. A statement on a table this same branch creates (empty, unread by deployed code) has no lock or rollout harm — no finding. Table size is a premise: cite where you saw it (a comment, a seed, the table's role) or say it is unknown and rate on what is known. Keyword case, formatting and naming are not findings.
