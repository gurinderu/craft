reconciler / controller and retry-loop correctness. READ the craft:distributed-races catalogue (its path is in the RACE CATALOGUE line below): it holds the question, the answer needed and WHERE to read it for every class R1–R20. A reconcile must converge from every state another actor can leave behind. ENTRY FIRST: before the diff, open the driver of the reconcile loop the changed code runs under — where the controller is built and run (e.g. `Controller::new(..).owns(..).watches(..).run(reconcile, error_policy, ..)`, a `watcher` stream, a work-queue worker) — and note its watches, predicates and generation filters, its error policy and requeue intervals, and its concurrency (how many reconciles run at once, for one object and across objects); cite that file:line in `whereChecked`. Its watches and error policy answer R1 and R2, so they are read, not assumed. Then MAP the primary object, every child it writes, every object it READS that another controller owns, and every requeue/error outcome the pass can return. Then answer each class from its carrier, not from comments, for EVERY instance in the diff, not the first convenient one. R1–R6 need evidence from OUTSIDE the diff: (R1) self-triggering write — enumerate EVERY write to the primary in a pass, including the status/conditions the generic driver/error path writes on every pass (holds and errors included): does it change a field every pass (lastTransitionTime), does the primary's own watch (no predicate / no generation filter) re-enqueue it sooner than the requeue the code relies on, and is it skipped when nothing changed? (R2) wake source — for EVERY outcome the requeue/error policy can return (await-change included), what event or timer guarantees a pass by the deadline the code promises? None → the bound is fiction. (R3) foreign stale cache — not our own stale read (that is R12): for EACH object another controller owns that a release/delete/label removal depends on, name that controller and its observed-generation gate (an applied/desired generation pair, e.g. status.observedGeneration vs metadata.generation); can it still act (recreate a child from the OLD template) after we decided from its absent/finished state? The decision must wait until its observed generation catches up. Read that controller's code. (R4) permissions — check every API verb/resource the diff newly calls against the shipped Role/ClusterRole/chart; a missing grant is a 403 only a real cluster shows. (R5) protection released on a change of intent (spec) instead of end of use, when the consumer outlives the spec. (R6) migration window — objects created before this change lack a field/label/status the new logic relies on: what does the new code do with them, delete path included? R7–R20 (create/patch divergence, partial-failure strand, cleanup, status churn, feature gate, 409/404 race, swallowed error with no timer, strict decode on a shared stream, webhook failurePolicy, retry bound lost on an error path, a hold only an unwatched object clears, a status write from a cached snapshot with no resourceVersion fence, no UID fence between selecting and mutating, an external-system claim not checked against its pinned source) — work them from the catalogue. If the catalogue cannot be read, R1–R6 above stand on their own and you say so. STALE OR RECREATED OBJECT: for each object the pass reads and later acts on (deletes, patches, releases, frees an external resource for), name what proves it is STILL the same object at the write — a UID precondition or check, a resourceVersion on the write, an observed-generation compare — or the interleaving that breaks it: the object deleted and recreated under the same name between the read (or the cached event) and the write, so the pass acts on the new one with the old one's decisions; a value cached in memory or in an annotation keyed by name, not UID; a status written from a snapshot older than the spec it reports on. CONCURRENT CONTROLLERS: for each field or child another controller (or a second replica during a rollout, or the old and new version side by side) also writes, play the two writers out and say who wins and whether the loser re-converges or fights forever. REQUEUE: for each outcome of the pass (ok, error, a hold, waiting on another object), say when the next pass runs and what wakes it; an error swallowed into Ok with no requeue, or a requeue that drops the backoff, is a finding. EARLY EXITS (review-rules sweeps.md §2): list every early return, hold, refusal and degraded hook of the changed pass, diff the maintenance steps each skips (status, latch release, cleanup, recorded progress, scheduled wake-up) against the full path, and name the state that wedges or drifts. A question you cannot answer from evidence is an open finding, not a pass; name the interleaving or request order that produces the bad state. DELETION/RECOVERY FLAG: set `deletionOrRecoveryPath: true` on a finding whose defect sits on a deletion or recovery path (finalizer removal, teardown, a delete handler, crash or partial-failure recovery); the engine floors such a finding at Medium only when its `harmLevel` is operator-recovery or worse (the Severity floor section of the catalogue is the rule) — the floor does not invent a harm. Leave it unset otherwise.
