SQL queries — in `.sql` files and in query strings embedded in code of any language (sqlx/diesel/postgres calls in Rust, query strings elsewhere): whether each changed query does what the code around it needs, against the schema the repository actually has (PostgreSQL semantics unless the repository names another engine). Load the sql-review skill and work its queries checklist. Read the schema first: the migrations or schema files of the tree at HEAD that create and alter every table and column the query names — never assume a column's type, nullability or index. For EACH changed query: (1) SCHEMA MATCH: every column exists with the type the code binds and decodes (a nullable column decoded into a non-optional type fails at run time; an outer join makes the joined side nullable; text compared to a number, a timestamp to a timestamptz); NULL semantics — `= NULL` is never true, `NOT IN (subquery)` returns no rows when the subquery yields a NULL, SUM/MAX over no rows return NULL while COUNT returns 0; a WHERE on the right table of a LEFT JOIN turns it into an inner join; a join on an incomplete key multiplies rows and every aggregate over them, and a DISTINCT that hides it. (2) TRANSACTIONS AND ISOLATION: a read-then-write across statements (check a balance, then update it; select, then insert if absent) outside one transaction, or inside one at READ COMMITTED (the PostgreSQL default) without `SELECT … FOR UPDATE`, a conditional UPDATE, a unique constraint or ON CONFLICT — a lost update or a duplicate; at REPEATABLE READ or SERIALIZABLE, a serialization failure (SQLSTATE 40001) or deadlock (40P01) the caller never retries; a statement meant for the transaction sent on the pool instead (sqlx: `&pool` where `&mut *tx` was meant), so it commits on its own; a transaction held open across a network call or an await on something slow. (3) INDEX: a new or changed WHERE, JOIN or ORDER BY on a table that grows, with no index whose leading columns serve it — find the indexes in the migrations; a function or cast on the indexed column (`lower(email)`, `col::text`) or a leading-wildcard LIKE defeats a plain b-tree. (4) N+1: a query run once per row of another query or per item of a loop — name the loop and the row count it scales with; the fix is one query (a JOIN, `= ANY($1)` over an array bind). (5) INJECTION: a query text built from a value (format!, concatenation, an f-string, `EXECUTE` of a concatenated string) instead of a bind parameter, an identifier not quoted with quote_ident/format('%I') — `security` when the value can come from outside. HARM: wrong rows returned or written is `data-loss` when it corrupts stored data and `intent-unmet` when the query does not do what the change says; a query that takes a table-wide lock or scans a large table on a hot path, or a pool exhausted by an N+1, is `outage` only when you name the traffic that makes it one, else should-fix at most. A query on a table that cannot grow (a fixed lookup table) needs no index. Keyword case, formatting and alias naming are not findings.
