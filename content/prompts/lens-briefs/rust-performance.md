performance & needless allocation (load the rust-performance skill): allocation in a hot loop (PER-001); `Vec::new()` + push where the size is known — `with_capacity` or collect from a sized iterator (PER-002); N+1 queries / repeated work in a loop (PER-003). And the NEEDLESS-ALLOCATION list — an owned value built where the code only reads it: (a) `collect()` into a Vec only to iterate it, take its `len()` or call `contains` — iterate the iterator, `.count()`, `.any()` (PER-004); (b) a fn returning `Vec`/`String` that its callers only iterate or read, where `impl Iterator<Item = …>` or a borrow (`&str`, `&[T]`) would do — e.g. a `scopes_vec()` that allocates a Vec of Strings for a caller that walks it once (PER-005); (c) a parameter typed `&[String]`/`&Vec<String>`/`&String` that forces callers holding `&str`s to allocate, where `&[&str]`, `impl IntoIterator<Item = impl AsRef<str>>` or `&str` serves them (PER-006); (d) `clone()`/`to_string()`/`to_owned()`/`format!` used only to satisfy a borrow, or inside a loop where the value could be borrowed or built once (PER-001); (e) a lookup key built into a `String` (`format!`, `to_string`, concatenation) only to call `get`/`contains_key` — look up by `&str` through `Borrow`, a tuple or newtype key, or build the key once outside the loop (PER-007). SEVERITY by harm: on a hot path — a loop, a request handler, a fn called per item or per request — say which, and the finding is should-fix (Medium); otherwise Low. Not a finding: a one-off allocation at start-up, in a test, in a CLI's argument handling or on an error path; a clone the borrow checker genuinely needs (shared ownership across threads/tasks, a value moved into a closure) — say why it is needless before you file it. ROLL UP: instances of the same pattern go into ONE finding that names the pattern with a representative file:line and the count (raise an instance on its own only when it alone sits on a hot path the others do not).
