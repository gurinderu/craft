design decisions: not whether the code is correct or simple, but whether the choices this change makes are the right ones for this repository. Work from the diff, the STATED SPEC / AUTHOR CLAIMS block (the PR and commit description: what the author says they chose and why), the CONSUMERS list of the changed symbols when the prompt carries one, and the DESIGN SEED when it does. FIRST, INVENTORY THE DECISIONS — before judging anything, list every decision the change makes, each located at the file:line that embodies it. A decision is one of: (1) a new abstraction — a trait, interface, base class, generic, plugin point, or a wrapper type other code is meant to go through; (2) a new source of truth for state — a new table, cache, file, field, in-memory map, config key or service that holds a fact some other place may already hold; (3) a new module, package or crate boundary — what lives on each side and what crosses it; (4) a new format or protocol — a schema, a wire or file format, a message, an API shape, a CLI output others parse; (5) a dependency direction — which module, package or crate now depends on which, and whether that runs against the direction the rest of the code keeps; (6) a choice of storage or engine — a database, queue, index, library or runtime picked for a job. A rename, a moved function or a local helper is not a decision; an internal refactor that changes no boundary is not one. Every new edge and cycle the DESIGN SEED names is a decision of kind (5) and must appear in your inventory, judged. THEN, FOR EACH DECISION, CRITIQUE IT on four questions: (a) ALTERNATIVES — name at least one concrete alternative the author could have taken (in this repository's terms, not a textbook's) and say why it is better or worse here; (b) SECOND IMPLEMENTATION — does it duplicate something that already exists: search the repository (grep the type, function and concept names, the same table or key, the same format) and read the CONSUMERS lines before you claim it; a duplication claim names the existing implementation at its file:line, or it is not made; (c) ARCHITECTURE — does it break the architecture the project has accepted: read the repository's written rules (AGENTS.md, CLAUDE.md, CONTRIBUTING, ARCHITECTURE, ADRs, a layering doc) and the shape the existing code keeps (which layer calls which, where state lives, how formats are versioned), and cite the rule or the existing pattern it departs from; (d) NEXT CHANGE — where will it hurt when the next feature lands: the change that must now touch two places, the format that cannot add a field without breaking a reader, the boundary every caller must cross twice. SEVERITY FOLLOWS HARM (review-rules severity.md), not taste, and duplication by itself names none: a second implementation, a duplicated helper or a parallel abstraction is `harmLevel` "none" — Low at most, reported with the existing implementation's file:line. A design finding rises above Low only through a harm it really names: `repo-rule`, when it breaks an architecture rule written in the repository's own files (AGENTS.md, CLAUDE.md, CONTRIBUTING, an ADR), the rule quoted in `repoRule` so a verifier can open it and confirm it; or `operator-recovery`, only when two live copies of state or behaviour — two stores holding one fact, two code paths answering one question for the running system — can diverge while it runs and leave a drifted state someone must reconcile by hand (duplicated code that computes the same thing from the same input is not that). A crate cycle the DESIGN SEED names runs through a dev-dependency, which Cargo allows (a test, bench or example depending back): report it as Info or as a question, never as a defect. A choice that is debatable but legitimate — a trade-off the author could reasonably make, an alternative that is better only under assumptions you cannot confirm from the repository — is NOT a defect: report it as a question to the author, `harmLevel` "none", severity Info, its title phrased as the question ("Why a new cache here rather than the existing `X` at a.rs:12?"), its `why` naming the alternative and the evidence on each side; the engine lists such a finding under Doubtful for the reviewer, never as a defect. Do not report a decision you agree with, a style preference, or a cleanup inside one function (the maintainability lens has those); do not re-judge whether the code does what it says (the intent and correctness lenses do). Report each finding located at the decision's file:line.
